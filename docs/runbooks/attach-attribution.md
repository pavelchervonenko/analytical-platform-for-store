# Включение аналитической атрибуции гарантий

## Подготовка

Этот документ описывает процедуру; он не подтверждает её выполнение в production.
Проверить текущую среду по [project-state](../current/project-state.md). Включение выполняется
только после проверки локальных frontend и backend, интеграционных сценариев и сверки истории.
Релиз использует обычный deployment/ACL-контур; роли runtime получают права на новые
таблицы/представления/функции через существующие default privileges. Отдельных повышенных прав
пользователю приложения не требуется.

Дополнительная оптимизация source/target document fingerprint не требует backfill решений:
bytes, validity predicates, формулы и immutable history сохраняются. Перед релизом выполнить
`WarrantyFingerprintContextMigrationIntegrationTest`, существующие warranty integration tests
и полный backend check. Synthetic mixed-load timings не заменяют оценку backlog/latency на
данных среды; published миграции не редактировать, constraints и timeouts для обхода не отключать.

1. Применить миграции новой сборки при выключенном переключении аналитики. Денежные таблицы
   не переклассифицируются и значения сумм/финансового сотрудника не переносятся.
2. Проверить контракты source employee. `ReturnSyncPersistence` сохраняет
   `processingEmployeeExternalId` отдельно; в текущем адаптере это `detail.customer.id`.
   Согласование с сотрудником строки подтверждалось существующей сверкой
   [выгрузки LiveSklad](../history/audits/2026/09/LIVESKLAD_PRODUCTION_RECONCILIATION_2026-01_MAGAZIN.md).
   Не переносить payload, персональные данные или изображения отчётов в evidence.
3. Подготовить историю ограниченными проходами ниже. Потерянный raw не восстанавливать догадкой.
   При необходимости повторно синхронизировать источник штатным recovery-контуром.
4. Сравнить N/B по 14 метрикам, финансовые суммы и сотрудников до/после, особенно возвраты
   другого месяца, Care, ASIS, неизвестных сотрудников, смешанные документы и частичные возвраты.
5. Включить `ATTACH_ATTRIBUTION_ENABLED` согласованно у API и worker. Сначала локальный/тестовый
   магазин с синтетическими данными; глобальный флаг не является выбором одного production-магазина.
   Перед включением в рабочей среде разобрать backlog и оценить долю предварительных показателей.

## Ограниченный backfill source employee

Использовать `scripts/attach-source-employee-backfill.sql` через штатное безопасное подключение
psql. Credentials только в окружении, не в командной строке или evidence. Обязательные переменные:
`store_id`, `period_start`, `period_end`, `after_id`, `apply`. Период — не больше 366 календарных дней,
пачка — максимум 500 документов, стартовый cursor — нулевой UUID. `apply=false` делает dry run;
`apply=true` заполняет только отсутствующий аналитический ID. Неверный диапазон даёт пустую пачку:
оператор обязан проверить границы до запуска.

Скрипт читает только raw-версию, на которую указывает текущий документ, с совпадающими
connection/store/external ID и RETURN_DOCUMENT. Также должен совпадать `detail.id`. Нет полного
payload в выводе: только scanned/recoverable/missing_evidence/updated/invalidated_stores/next_cursor.
Он не меняет денежные суммы, employee_id, version или updated_at финансового документа.
Повторная запись уже заполненного значения не выполняется.

Для каждой пачки сначала выполнить dry run, затем apply с тем же cursor и границами. Продвигать
cursor из результата apply; если сначала пройти всю историю в dry run, перед apply начать снова
с нулевого cursor. Продолжать до scanned=0. Missing evidence фиксируется агрегированным числом;
неизвестный сотрудник остаётся не назначен, а затронутое employee-сравнение — неполным.
Raw retention не удаляет уже сохранённый аналитический ID.

## Разбор и проверка

Руководитель открывает «Разобрать конфликты» на странице обзора. Очередь относится ко всей истории
его магазина. Выбирает исходное устройство или гарантию возврата, распределяет количество,
проверяет даты/продавцов и сохраняет. Для исключения/откладывания указывает причину. Исправление
прошлого решения доступно в фильтре решённых; создаётся новая ревизия.

HTTP 412 требует обновить карточку и заново проверить устройства. Сетевой сбой допускает повтор
с тем же idempotency key. Полнота распределения защищена API и deferred constraint в БД;
история не редактируется. Предупреждения доступны отдельным фильтром и не требуют исключать
правильно связанную гарантию.

После решения live-метрики обновляются при следующем чтении, frontend инвалидирует запросы
магазина. Текущий Weekly Review читает durable invalidation и повторно оценивает facts: новая
детерминированная ревизия создаётся только при изменении содержимого, иначе сохраняется прежний
snapshot ID/hash. Legacy v2 подтверждает точный marker БД из того же RR-чтения, а не время JVM;
решение после чтения остаётся неподтверждённым. Старый wall-clock checkpoint при несовпадении
вызывает повторную проверку без принудительной новой revision. Planner также проверяет invalidation.
Не исправлять это вручную изменением `changed_at`, `checked_through`, часов или payload.
Это не вызов платного AI. Старые месячные/годовые
снимки и обогащения сохраняются. Для нового отчёта использовать штатное создание новой версии,
не UPDATE опубликованного payload.

## Разбор аксессуаров с неясным назначением

В том же окне «Разобрать конфликты» открыть вкладку «Аксессуары». Очередь
включает неопределённые и универсальные чехлы, неопределённые защитные стёкла
и требующие проверки защитные плёнки, зарядки и аксессуары AirPods/Watch. Она показывает тип, код, название, чек и предполагаемый бренд.
Варианты назначения поступают от сервера: чехлы — iPhone/Samsung/другое устройство;
стёкла — iPhone/Samsung/другой телефон; плёнки — телефон/не телефон;
спорная зарядка — телефонный CHARGER_CABLE, аксессуар Apple Watch или NO_ATTACH.
Для спорного аксессуара AirPods/Watch выбирается его роль либо NO_ATTACH.
NO_ATTACH — подтверждённое отсутствие вклада, не другая денежная категория.
CURRENT-товарная роль применяется автоматически; отзыв не меняет сохранённую роль
старой продажи. Неактуальная продажа/связь возврата требует новой per-sale ревизии,
не изменения неизменяемого снимка и не UPDATE всей истории.
Для каждого типа доступно отложенное решение `DEFER`. Оба бренда в чеке —
конфликт; один бренд — только подсказка. Перед подтверждением сверить
маркировку упаковки, точный артикул или документ поставщика. Одного чека
недостаточно. Если совместимость неизвестна, выбрать `DEFER` и указать,
что нужно запросить; для явно другого устройства выбрать
`CASE_OTHER_DEVICE` с основанием. Решение действует на одну строку продажи,
не на все продажи той же карточки. Если код LiveSklad смешивает модели,
разделить карточки в источнике отдельной операцией, не распространять
одну проверку на всю историю автоматически.

Перед сохранением проверить preview и даты связанных возвратов. После
сохранения обновить показатели периода и убедиться, что подтверждённый
числитель изменился только у выбранной цели и её сводки, без второго зачёта. Предположение уменьшается только
если чек до решения содержал телефон одного бренда; конфликт в него не входил.
Суммы продаж и зарплатная категория не меняются. Устаревший ETag (412)
требует открыть карточку заново. Возврат без надёжной ссылки на исходную
строку не приписывать по названию: сначала восстановить связь штатным
контуром возвратов и перепроверить показатели. Счётчик возвратов без точной связи
за период показан во вкладке «Аксессуары»; несовпадение товара, исходного документа,
подключения, магазина или порядка дат тоже требует проверки; ненулевое значение означает риск
завышения подтверждённого attach-rate. Опубликованный отчёт
сохраняется; при необходимости создать новую версию.

Сохранение решения и обновление экрана — разные операции. Если показано
«Решение сохранено», но обновление показателей не удалось, не сохранять решение повторно:
использовать кнопку повторного обновления. Это касается и гарантий, и аксессуаров.
При успешном обновлении перечитываются зависимые показатели магазина; сохранённые
опубликованные отчёты не переписываются.

## Откат и ограничения

Выключение настройки возвращает чтение v3 и блокирует новые решения, сохраняя историю.
Это возврат к прежней методике, а не сохранение новых аналитических значений. Обратное удаление
таблиц, решений или миграции не требуется. После повторного включения fingerprints снова
определяют актуальность решений.

Неизвестные исходные периоды консервативно ограничивают гарантийный benchmark всего магазина.
Межмагазинные связи не поддерживаются. Для большого числа ручных распределений/возвратов нужно
отдельно проверить запросы на репрезентативном объёме перед рабочим включением. Локальный
синтетический тест не подтверждает производительность на размере всей production-истории.
