# ИИ-разбор — контракт интерфейса этапа 5

Дата: 2026-08-27
Статус: реализован локально, production rollout не выполнялся

## Задача экрана

Экран помогает руководителю магазина за несколько минут ответить на четыре вопроса:

1. как завершилась последняя полная неделя;
2. что изменилось относительно предыдущей полной недели;
3. что повлияло на результат;
4. что проверить или сделать на следующей полной неделе.

Месячный план, текущая незавершённая неделя, технические версии схем и состояние provider job на
этом экране не показываются. План остаётся на главной странице и в «Плане и сменах».

## Порядок чтения

Интерфейс использует один вертикальный сценарий без вкладок и параллельных трактовок:

1. период, база сравнения и готовность данных;
2. один главный итог;
3. краткие выводы о положительной динамике, риске и приоритетном действии; числовые подробности
   остаются ниже в результатах и факторах;
4. четыре результата: чистая выручка, валовая прибыль, маржа, средний чек;
5. основные изменения и не более трёх следующих шагов;
6. свёрнутая структура продаж;
7. агрегированная картина команды;
8. отдельные раскрываемые карточки сотрудников;
9. ограничения данных — только если они есть.

Подробные evidence раскрываются по действию «Основание» и не конкурируют с основным текстом.
Формула чистой выручки и структура продаж также свёрнуты по умолчанию.

## Граница «Команда» / «Сотрудники»

«Команда» отвечает только за общую картину:

- сколько сотрудников имели продажи;
- сколько участвуют в корректном сравнении;
- сколько требуют внимания;
- не более двух агрегированных наблюдений;
- понятное описание benchmark.

В «Команде» запрещены ФИО, персональные показатели и персональные действия.

«Сотрудники» содержит единственный персональный контур:

- имя и участие в сравнении;
- выручку и долю допродаж в свёрнутой строке;
- продажи, чистую выручку, долю допродаж и выручку в час после раскрытия;
- собственную недельную динамику;
- сравнение с медианой магазина при достаточной базе;
- сильную сторону, зону внимания и персональный следующий шаг.

Первые восемь карточек видны сразу. Более длинный список раскрывается одной кнопкой.

## Состояния

| Состояние API | Поведение интерфейса |
| --- | --- |
| READY | Полный разбор без предупреждения о качестве |
| PARTIAL | Доступные блоки остаются видимыми, сверху одно компактное предупреждение |
| BLOCKED | Результаты не показываются; объясняется, каких данных не хватает |
| PREPARING | Нейтральное состояние формирования с автоматическим обновлением |
| 404 | Спокойное пустое состояние до первой weekly-review revision |
| network/schema error | Стандартная ошибка запроса с повтором |

Для `SummaryBlock`, `SalesStructureBlock` и `TeamBlock` дополнительно применяется локальный
`BlockState`:

- `LIMITED` сохраняет рассчитанные значения и показывает компактную метку ограничения;
- `INSUFFICIENT` не показывает значения блока и объясняет нехватку данных;
- `NOT_APPLICABLE` показывает отдельное нейтральное состояние;
- пустые factors, actions, team observations и employees не исчезают бесследно, а дают одну
  короткую бизнес-подпись.

Ограничение относится только к затронутым блокам. Ошибка последней синхронизации не подменяет
качество закрытой недели, если её источники покрыты полностью.

## Визуальные правила

- используются шрифт, сетка, фон, границы и основной синий цвет приложения;
- один внешний контейнер и разделители вместо набора конкурирующих панелей с тенями;
- зелёный и красный обозначают эффект показателя, а не направление числа;
- служебные версии, ID, коды и provider status пользователю не показываются;
- тексты короткие; пояснение выводится только там, где меняет управленческое решение;
- выводы, причины и действия читаются последовательно сверху вниз на всех ширинах;
- desktop использует колонки только для компактных итоговых сигналов и KPI;
- tablet переводит итоговые сигналы в последовательный поток при нехватке ширины;
- mobile использует сетку 2×2 для четырёх KPI и метрик раскрытого сотрудника, три компактных
  счётчика команды, скрывает второстепенную метрику в заголовке сотрудника и сохраняет нативные
  раскрытия details/summary; одна колонка KPI остаётся только для ширины до 360 px;
- горизонтальный скролл страницы запрещён.

## Доступность

- один h1 принадлежит странице, блоки используют последовательные h2–h4;
- все раскрытия доступны с клавиатуры и имеют нативное состояние;
- иконки декоративны и исключены из accessibility tree;
- PREPARING и пустое состояние используют aria-live;
- BLOCKED и блокирующие проблемы используют alert semantics;
- цвет не является единственным носителем смысла: рядом всегда есть текст;
- при prefers-reduced-motion переходы отключаются.

## Техническая интеграция

Frontend читает только:

    GET /api/stores/{storeId}/weekly-reviews/current

Ответ проходит runtime-проверку Zod weeklyReviewSchema. Схема дополнительно проверяет:

- коды, units и порядок четырёх core-метрик и revenue decomposition;
- две смежные завершённые недели понедельник–воскресенье и арифметическое равенство
  `salesRevenue - returnRevenue = netRevenue` для обоих периодов;
- фиксированные employee metric codes/units и допустимые enum actions/sort groups/scopes;
- готовность, materiality и effect каждого factor, а также принадлежность персонального action;
- совместимость `reportState`, quality counters и обязательного summary outcome;
- уникальность factor/action/employee/structure IDs;
- разрешение evidence для всех metric, narrative, factor, structure, attach, team, employee,
  peer, action и limitation references.

Frontend fixture не составляется вручную. Golden JSON в
`frontend/src/test/fixtures/weekly-review-v2-ready.json` получен сериализацией реального
`WeeklyReviewResponse`, собранного production `WeeklyReviewAssembler`, и затем проходит ту же Zod
схему, что сетевой ответ.

Старый WeeklyInsightView и endpoint v21/schema3 остаются в коде как rollback-compatible path, но
маршрут /insights локально переключён на WeeklyReviewView. Commit и deploy выполняются только
после отдельного решения.

Главный итог deterministic fallback формулируется как сравнение направлений чистой выручки,
валовой прибыли и маржи. Доказанный арифметический вклад возвратов добавляется отдельным
предложением. Положительное изменение без рассчитанного вклада не называется причиной общего
результата. Заголовки факторов формируются по виду показателя и не зависят от грамматического рода
исходной подписи.

## Проверка перед rollout

- component tests для READY, PARTIAL, локальных LIMITED/INSUFFICIENT/NOT_APPLICABLE, BLOCKED,
  PREPARING, 404/retry, network error, limited metrics, пустых бизнес-блоков и раскрытия сотрудника;
- contract/presentation tests для backend golden, report/block invariants, completed-week boundaries,
  revenue identity, factor/action semantics, enum/scopes, порядка и units KPI, полного evidence
  graph, NO_BASE, unit formatting и effect tone;
- полный frontend check;
- локальные screenshots /insights на desktop 1440, tablet 768 и Pixel 7;
- отсутствие горизонтального overflow, console errors и HTTP 5xx;
- независимый UX/code review;
- canary с реальным v2 snapshot каждого магазина до массового переключения.
