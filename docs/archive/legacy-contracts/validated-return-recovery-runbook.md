# Безопасное восстановление подтвержденных возвратов LiveSklad

Актуальность: 2026-08-24.

Runbook применяется только к возвратам, которые подтверждены отчетом CRM и для которых известны
внешний ID, номер документа и ожидаемые контрольные значения. Это не замена backfill и не способ
«подправить цифру» вручную.

## Почему используется штатный API

Endpoint

`POST /api/admin/integrations/livesklad/returns/recoveries`

создает durable recovery job. Worker повторно получает документ из LiveSklad и проверяет:

- совпадение external ID;
- вид документа `RETURN`;
- номер документа;
- ожидаемую чистую сумму;
- ожидаемое количество позиций;
- идемпотентность повторного запуска.

Несовпадение не меняет аналитические факты и завершается
`RETURN_RECOVERY_EXPECTATION_MISMATCH`. Временные ошибки повторяются по политике worker.
Состояние читается штатным status endpoint по ID recovery.

## Предварительные условия

1. Есть письменное основание: отчет сверки, магазин, период и номер возврата.
2. External ID получен из LiveSklad, а не угадан по номеру.
3. Зафиксированы ожидаемые сумма и количество позиций.
4. Production backup/monitoring исправны.
5. Нет выполняющейся синхронизации того же периода или другой операции, меняющей те же факты.
6. Авторизованный оператор использует ADMIN session и CSRF-механизм штатного API.
7. Секреты и session cookie передаются только через окружение/secret storage и не попадают в
   shell history, логи и документы.

## Выполнение одной записи

1. Сформировать request без персональных данных:

```json
{
  "externalId": "<livesklad-return-id>",
  "expectedDocumentNumber": "<return-number>",
  "expectedNetAmount": 1.00,
  "expectedPositionCount": 1,
  "reason": "<ссылка на сверку и период>"
}
```

2. Сгенерировать уникальный `Idempotency-Key` для конкретного документа и операции.
3. Заменить демонстрационные `1.00` и `1` точными положительными значениями из CRM-отчета и
   отправить POST через штатный аутентифицированный клиент.
4. Сохранить recovery ID и correlation ID в change record.
5. Опросить status endpoint до terminal state.
6. При `PROCESSED` проверить сам документ и агрегаты магазина/сотрудника за дату возврата.
7. При mismatch ничего не обходить: сверить ID, сумму, позиции и исходную продажу.
8. Повторить запрос с тем же `Idempotency-Key` можно безопасно; новый ключ используется только
   после явного решения о новой операции.

## Пакетное восстановление

Для нескольких документов сначала выполнить dry review таблицы:

| Поле | Обязательно |
| --- | --- |
| Магазин и период | Да |
| Номер возврата | Да |
| External ID | Да |
| Ожидаемая чистая сумма | Да |
| Ожидаемое число позиций | Да |
| Основание/отчет | Да |
| Уникальный idempotency key | Да |

Записи отправляются последовательно. После каждой terminal-записи проверяется результат; массовый
fire-and-forget запрещен. По завершении повторяется сверка CRM ↔ приложение за тот же включительный
период.

## Проверка результата

- возврат существует в `sales_documents` как `RETURN`;
- сохранены позиции и связь с исходной продажей, если она доступна;
- выручка, валовая прибыль и показатели продавца изменились ожидаемым образом;
- quality issue не скрыт искусственно;
- повтор той же операции не создает второй финансовый эффект;
- итоговая разница с CRM равна нулю либо имеет документированное внешнее объяснение.

## Аварийная остановка

Остановить пакет при первом из событий:

- `RETURN_RECOVERY_EXPECTATION_MISMATCH`;
- неожиданный магазин, сотрудник, сумма или состав;
- рост HTTP 5xx/DB ошибок;
- нарушение health/readiness;
- расхождение стало больше.

Нельзя напрямую вставлять строки в финансовые таблицы, менять terminal state recovery или
отключать проверки ожиданий.

## Политика временных скриптов

Локальный каталог `.codex-prod-recovery/` не является частью продукта и не должен попадать в
релиз автоматически. Одноразовый скрипт остается незакоммиченным, потому что он:

- привязан к конкретным июльским документам;
- выполняет production mutation;
- не является повторно используемым интерфейсом продукта.

Если нужен постоянный batch-инструмент, его следует реализовать отдельно: обязательные dry-run и
production guard, чтение входа без секретов, idempotency, bounded concurrency, тесты, аудит,
документация и code review. До этого источником истины остается validated recovery API.
