# Изоляция магазинов и целостность смен

Статус: реализация и итоговая проверка завершены 2026-09-19.

## Цель и границы

План устраняет взаимное влияние магазинов в сменах и закрепляет одинаковую серверную, клиентскую
и тестовую границу `пользователь -> магазин`. Он охватывает планы, показатели, структуру продаж,
сотрудников, отчёты и смены. Видимость зарплатных данных внутри отчётов не меняется, но такие данные
обязаны оставаться ограниченными выбранным магазином.

## Обязательные инварианты

1. Руководитель видит в каталоге и может запросить только назначенные ему магазины.
2. Идентификатор объекта из другого магазина не расширяет доступ и не меняет данные текущего.
3. Планы, показатели, структура продаж, сотрудники, отчёты и смены всегда вычисляются в границе
   `store_id`, включая фоновые расчёты и кеш клиента.
4. Один глобальный сотрудник может иметь смену в двух магазинах в один день; записи не конфликтуют.
5. Новую смену можно назначить только активному сотруднику с активным назначением и
   `participatesInRanking=true` в этом же магазине.
6. Изменять состав участников смен может только пользователь с функцией `SHIFTS` и доступом к
   магазину.
7. `ETag` и возвращаемый состав дня относятся к одной согласованной версии.
8. Смена магазина или месяца закрывает редактор и исключает отправку старого черновика в новый
   контекст.
9. Конфликт при очистке дня не удаляет незнакомые пользователю параллельные изменения без нового
   подтверждения.
10. Новые store-scoped endpoints не могут пройти архитектурную проверку без явной проверки доступа
    к `storeId`.

## Порядок реализации

1. Заменить глобальную уникальность смены на `(store_id, employee_id, work_date)` и проверить
   общего сотрудника в двух магазинах.
2. Закрепить серверные roster-инварианты и право `SHIFTS` для управления участием.
3. Сделать чтение ревизии и состава дня согласованным и покрыть настоящими конкурентными тестами.
4. Привязать состояние редактора к магазину и месяцу; изменить поведение конфликтующей очистки.
5. Расширить архитектурную проверку на все эффективные пути `/api/stores/{storeId}/...` и
   негативные IDOR-сценарии.
6. Обновить current-контракты, провести локальную визуальную проверку изменённых экранов и запустить
   backend, frontend и документационные проверки.
7. Выполнить итоговое code review и закрыть рабочий документ только после подтверждения всех
   инвариантов.

## Матрица приёмки

| Сценарий | Ожидаемый результат |
|---|---|
| Аккаунт A запрашивает каталог | В нём отсутствует магазин B |
| Аккаунт A подставляет `storeId` магазина B | `403`, без данных и побочных эффектов |
| Аккаунт A подставляет ID отчёта, сотрудника или смены магазина B | Отказ без изменения объекта |
| Общий сотрудник назначен A и B на одну дату | Обе смены существуют независимо |
| Сотрудник не участвует в рейтинге | Новая смена отклоняется сервером |
| Пользователь без `SHIFTS` меняет участие | `403` |
| Два пользователя редактируют один день | Изменения объединяются либо предъявляется явный конфликт |
| Очистка конфликтует с новой записью | Требуется новое подтверждение актуального состава |
| Магазин меняется при открытом редакторе | Старый редактор закрывается, запрос не уходит в новый магазин |
| Logout/login другого аккаунта | Данные и кеш первого аккаунта не отображаются |

## Промежуточное code review

После каждого пункта проверяются: направление внешних ключей и уникальностей, server-side
authorization, отсутствие доверия к frontend-фильтрам, атомарность транзакций, поведение старых
данных, коды ошибок, инвалидация кеша и полнота негативных тестов.

## Критерий закрытия

Все инварианты подтверждены автоматическими тестами и локальной проверкой интерфейса; миграция
безопасно применяется к существующим данным; current-документация описывает фактическое поведение;
итоговый diff-review не обнаруживает способа прочитать или изменить чужой магазин.

- [управление roster сотрудников](../current/api/employee-rating.md).

Backend проверяет доступ к магазину на всех эффективных путях `/api/stores/{storeId}`, а
интеграционная матрица подтверждает отказ для чужого магазина по показателям, структуре продаж,
сотрудникам, планам, сменам, отчётам, зарплате и еженедельным материалам. Миграция V52 и реальные
PostgreSQL-тесты подтверждают независимые смены общего сотрудника в двух магазинах, согласованность
`ETag` с составом дня и сериализацию конкурентной записи.

Frontend привязывает календарь и черновик к `storeId` и месяцу, очищает query cache при смене
аккаунта, не показывает управление roster без `SHIFTS` и не повторяет конфликтующую непустую
очистку без нового подтверждения. Контрактные, lint, component, backend, migration, concurrency,
security и documentation checks завершены. Локальные desktop, tablet и mobile снимки `/shifts` и
`/employees` просмотрены без переполнения или наложения элементов; сами снимки не сохраняются в Git.
