# Гарантии: независимая атрибуция attach-rate к устройству

Реализация подготовлена 2026-09-22. Текущие решения закреплены в
[ADR-0003](../decisions/ADR-0003-warranty-attach-attribution.md) и
[контракте attach-rate](../current/product/attach-rate.md). Проектные варианты ниже сохраняют
контекст обсуждения; статус проверки среды см. в runbook, не выводить его из этого проекта.


## Статус

Документ отделяет подтверждённые требования от предлагаемых решений и открытых вопросов.

Документ используется как источник бизнес-правил. Его команды «проанализируй загруженный

переделываются по обсуждаемой здесь модели, а не возвращаются к прежней атрибуции.

### Общие правила

- Attach-rate — отношение чистых количеств единиц допов и релевантной техники, не выручки,
  чеков или уникальных устройств с хотя бы одним допом. Несколько допов считаются поштучно.
- `N = продажи допов − возвраты допов`, `B = продажи техники − возвраты техники`;
  при `B > 0`: `max(0, N) / B × 100%`. Процент не ограничивается сверху значением 100%.
- Для `B <= 0` документ не задаёт результат; сохраняется действующий контракт приложения:
  процент `null`, в интерфейсе нет базы для расчёта. Это не нулевой attach-rate.
- Отрицательный исходный `N` остаётся в контрольной расшифровке; обнуляется отображаемый
  процент. Отдельные проблемы возвратов диагностируются без уничтожения исходных количеств.
- ASIS/ASIS+ относится только к новым iPhone. Нельзя переносить этот признак на Samsung,
  MacBook, iPad, Watch и другие устройства.
- Неоднозначные товары направляются на проверку; смысловая классификация и допустимые
  варианты написания не разрешают угадывать связь гарантии с устройством.
- Расчёт выполняется отдельно по продавцам. Матрица: строки — 14 категорий в порядке ниже,
  столбцы — продавцы. Для каждой ячейки доступны числитель, знаменатель и процент.
- Превышение 100% для обычных допов допустимо. Для гарантий это повод проверить количество
  и связи, но не основание молча обрезать результат до 100%.

### Граница новой модели гарантий

Две гарантийные строки сохраняют свои базы устройств, но получают отдельную связь и
аналитическую атрибуцию. Приоритет имеет требование пользователя: тип, период и продавец
берутся из устройства; финансовый факт не переносится. Название гарантии не определяет
единолично новую/Б/У базу. В смешанных случаях руководитель выбирает конкретные устройства,
а тип и аналитическую атрибуцию система выводит сама.

Три перечисленных Care-продукта остаются одной строкой «Премиум-сервис / Протекция».
Они не должны одновременно входить в новую очередь обычных гарантий или их числители,
даже если денежная классификация товара в текущей БД — `WARRANTY_GENERIC`.
Следовательно, нельзя определять охват нового resolver только по денежной категории товара:
сначала применяется подтверждённая семантика Care, затем — атрибуция обычной гарантии.

Ранее обсуждённая доля уникальных устройств с гарантией не заменяет поштучную формулу.
Если такой показатель понадобится, он проектируется отдельно; сейчас заказчик подтвердил
количество гарантий относительно количества устройств с диагностикой превышений.

### Результат статической сверки с реализацией

Базовая формула, clamp отрицательного числителя, отсутствие верхнего ограничения, порядок
14 строк, раздельные экран/камера и iPhone/Samsung реализованы в V38, AttachRateService и
OverviewManagementSections. Это сверка кода, а не подтверждение классификации всех фактических
товаров или чисел в production.

Отдельно зафиксированы расхождения и вопросы для приёмки:

1. По п. 18 пользователь 2026-09-22 явно выбрал сотрудника строки отчёта LiveSklad для
   возвратов остальных attach-категорий. Принятый ADR-0001 и текущая нормализация используют
   продавца исходной продажи; текущий employee attach читает ту же финансовую атрибуцию.
   Это подтверждённое изменение будущего attach-контракта, а не указание менять финансовый
   учёт. До реализации нельзя считать новое правило действующим. Нужен отдельный источник
   сотрудника для attach; сопоставление поля API со строкой отчёта требует проверки.
2. V38 считает `EarPods` ролью `AIRPODS`, а актуальный classifier относит проводные EarPods
   к `PODS_WATCH_OTHER_DEVICE`. В результате EarPods попадают в базу Pods/Watch, хотя
   по DOCX эта база ограничена AirPods и Apple Watch. В широкой базе протекции наушники
   допустимы. Исправление нужно делать в attach-семантике, не переписывая денежные категории.
3. Общие названия «переходник»/«адаптер», если они не совпали с более ранним правилом,
   classifier направляет в `OTHER_ACCESSORY_PRODUCT`. По DOCX переходники и адаптеры именно
   для зарядки/подключения относятся к зарядным/кабелям. Нужны положительные/отрицательные
   примеры назначения: переносить все адаптеры по одному слову нельзя.
4. Classifier включает `repair`/«ремонт» в `SETUP_SERVICE`, а fallback любого
   `ProductSourceKind.SERVICE` тоже даёт настройки. Это шире перечисленных услуг настройки
   и подготовки в DOCX; нужно отдельно сопоставить ремонтные услуги с нужным attach-охватом.
5. V38 использует буквальный regex названий Care после `lower`, без полноценной нормализации
   пробелов/вариантов написания. Приёмка должна проверить допустимые варианты, исключение
   физической защиты/установки покрытия и отсутствие двойного учёта с обычной гарантией.
6. UI сейчас подписывает единственную строку `PREMIUM_PROTECTION` как «Протекция».
   Требуемое заказчиком полное название — «Премиум-сервис / Протекция».

Эти пункты не означают, что в рамках чтения DOCX уже изменены формулы, classifier, UI или
финансовые факты. При реализации они должны получить отдельные проверки и актуализацию
действующих контрактов вместе с кодом.

### Подтверждённая атрибуция возвратов для остальных attach-категорий

Пользователь выбрал «Сотрудник строки отчёта LiveSklad». Это правило касается всех
attach-категорий, кроме двух переделываемых обычных гарантий; в частности, оно относится
к отдельной категории «Премиум-сервис / Протекция».

| Контур | Сотрудник возврата | Период |
|---|---|---|
| Остальные attach-категории | Сотрудник соответствующей строки отчёта LiveSklad | Период операции возврата, как в текущей формуле |
| Две обычные гарантии | Продавец устройства по подтверждённой аналитической связи | Период исходной продажи устройства по новой модели |
| Денежные показатели | Действующий финансовый контракт; эта договорённость его не меняет | Фактический период финансовой операции |

`LiveSkladReturnDetailPayload` уже содержит `processingEmployeeExternalId`, однако одно
название поля не доказывает его равенство сотруднику строки конкретной выгрузки. В реализации
нужно проверить соответствие и сохранить устойчивый source employee ID/его происхождение
отдельно от нормализованного финансового `sales_documents.employee_id`.

Изменять общий `employee_id` возврата для реализации этого требования нельзя: это затронет
выручку, GP, зарплату и другие показатели. Неизвестный или неразрешённый source employee
не заменяется молча продавцом исходной продажи; требуется видимое состояние «не назначен»
и диагностика. Удалённые/неактивные сотрудники не исключаются из полного store reconciliation;
видимость в рейтинге определяется его отдельным контрактом.

Приёмка включает исходную продажу у А и строку возврата у Б: для обычных допов возврат
уменьшает attach-количество Б, для связанной обычной гарантии — А, денежные показатели
сохраняют действующую атрибуцию. Дополнительно проверяются возвраты техники, влияющие на базу,
неизвестный source employee, исходная продажа вне периода и повторная синхронизация.
Перед rollout требуется новое решение, заменяющее только attach-часть ADR-0001, и
обновление product/API/rating контрактов; принятый исторический ADR не переписывается молча.

## Подтверждённые требования

1. Финансовые факты гарантии сохраняют фактические документ, дату, продавца, выручку,
   себестоимость и прибыль. Аналитическая связь не переписывает `sales_documents`, суммы
   `sales_document_items`, товарную классификацию или финансовую атрибуцию возврата.
2. Гарантийный attach-rate относится к типу, дате продажи и продавцу устройства.
   Поздняя отдельная продажа гарантии корректирует соответствующий исходный период.
3. База Б/У — Б/У iPhone и Samsung; новая база — новые/ASIS/ASIS+ iPhone и новые Samsung.
   iPad, Watch и другие устройства не подходят для этих двух показателей.
4. Единственный подходящий тип устройств в одном документе позволяет автоматическое решение.
   Несколько устройств одного типа не создают конфликта определения типа.
5. Смешанные типы требуют выбора конкретных устройств и распределения количества.
   Сумма распределений равна количеству гарантий, частично сохранённое решение не публикуется.
6. Отдельная гарантия связывается автоматически только через подтверждённый устойчивый
   идентификатор продажи, заказа или документа. Ручная связь тоже считается точной.
   Дата, клиент, имя продавца и название товара могут давать подсказку, но не автосвязь.
7. Неоднозначная, отсутствующая или неподходящая связь создаёт конфликт. Конфликтная гарантия
   не входит ни в один из двух числителей, но остаётся в денежных показателях.
8. Конфликт делает затронутый показатель предварительным и не должен штрафовать сотрудника
   в рейтинге. Заказчик уточнил: конфликт выносится на решение, после решения показатели
   обновляются. Предлагаемый механизм до решения — исключение затронутой гарантийной
   метрики из оценки, остальные метрики сохраняются; это не заморозка всего рейтинга.
9. Полный возврат гарантии обнуляет её вклад; частичный уменьшает количество. Возврат
   наследует связь исходной гарантии. Отсутствие исходной гарантии — конфликт.
10. Возвращённое устройство с активной гарантией создаёт отдельную проблему согласованности.
11. Решения доступны администратору и руководителю соответствующего магазина; это явно
    подтверждено заказчиком. Доступ к другому магазину запрещён и для поиска кандидатов.
12. Действия: выбрать устройство, найти исходную продажу, распределить количество,
    исключить из attach-rate с обязательной причиной, отложить. История содержит автора,
    время, основание и предыдущую/новую связь. Повторная синхронизация сохраняет решение;
    существенное изменение фактов открывает конфликт повторно.
13. Частичный возврат строки гарантий, распределённой между разными устройствами,
    без точного указания возвращённой гарантии создаёт конфликт. Пользователь выбирает
    возвращённую гарантию вручную; пропорциональное уменьшение не применяется.

## Текущее поведение и точки изменения

`attach_rate_item_facts_v3` относит `Check Discount` к Б/У, остальные подходящие `Check` —
к новым по названию товара. Даты и сотрудники берутся из финансового документа; привязки
гарантии к устройству нет. Этот способ нужно заменить только для двух гарантийных метрик.

`AttachRateRepository` и `EmployeeAttachRateRepository` должны читать одну новую проекцию.
Иначе показатели магазина, продавца и рейтинга разойдутся. `EmployeeRatingService` сравнивает
сотрудника со средним магазина; недостаточно исключить конфликт только из строки сотрудника,
оставив искажённый benchmark.

Другие attach-метрики сохраняют поштучную формулу и период операции; сотрудник возврата
меняется на сотрудника строки отчёта по явному решению пользователя 2026-09-22.
`PREMIUM_PROTECTION` — отдельный показатель; настоящее требование не переносит его
в две обычные гарантии.

Существующие `original_document_id` и `original_item_id` описывают возврат к исходной продаже.
Использовать их для связи отдельной продажи гарантии с устройством нельзя: это изменит
семантику финансовой нормализации и проверок целостности.

В текущих нормализованных DTO `LiveSkladSaleDetailPayload` и `LiveSkladSalePositionPayload`
нет подтверждённого идентификатора устройства/исходной продажи для отдельной гарантии.
До изучения фактического поля и его гарантий уникальности такие продажи требуют ручной связи.
Произвольное поле raw JSON или совпадение номера документа точной связью не считается.

## Предлагаемая модель данных

Отдельный домен атрибуции гарантий, без изменения финансовых фактов:

- Источник гарантии: стабильный ID строки продажи/возврата, магазин, подключение LiveSklad,
  количество и существенный отпечаток источника.
- Решение: ID, ревизия, источник `AUTO_DOCUMENT` / `SOURCE_REFERENCE` / `MANUAL`, состояние,
  автор, время и обязательное для ручного решения основание.
- Распределения: ссылка на строку устройства, количество, исходная строка гарантии для
  возврата, отпечатки обоих концов связи. Тип/период/сотрудник выводятся из устройства,
  а не принимаются как доверенные значения из браузера.
- История: неизменяемые ревизии решений, включая откладывание, исключение и повторное
  открытие после изменения источника. Текущее решение не заменяет журнал действий.
- Кандидаты: точные связи отдельно от рекомендаций, с причиной попадания в список.

Состояния: `RESOLVED_AUTO`, `RESOLVED_MANUAL`, `CONFLICT`, `EXCLUDED`, `DEFERRED`.
`DEFERRED` остаётся неразрешённым и не участвует в числителе; это не скрытое исключение.
Предупреждения независимы от состояния: превышение количества не отменяет установленный тип.

Один документ с несколькими устройствами одного типа позволяет определить тип/период/
продавца без выбора конкретного экземпляра. Нельзя произвольно выдавать такую групповую
связь за доказательство покрытия определённого серийного номера. Для последующего возврата
части устройств может понадобиться уточнение конкретного распределения.

Количество хранится как decimal совместимой с фактами точности; расчёты не используют float.
Разрешено превышение количества гарантий над базой с предупреждением, поэтому constraint
`allocated <= device quantity` здесь противоречил бы требованиям. При этом отрицательные,
нулевые, дублирующиеся и неполные распределения недопустимы.

## Повторная синхронизация и конкурентность

Отпечаток включает ID/тип документа, магазин/подключение, дату и продавца устройства,
ID товара/строки, количество, удаление, тип/состояние устройства и подтверждённую связь.
Обновление `last_sync_run_id`, времени загрузки или форматирования имени само по себе
не должно сбрасывать решение. Денежные поля не определяют тип устройства.

Команда сохраняет распределения и audit одной транзакцией. Версия решения и отпечатки
проверяются после блокировки источника и целевых строк в устойчивом порядке. Повторная
отправка той же команды должна быть идемпотентной; stale update возвращает конфликт,
интерфейс сохраняет черновик и предлагает проверить новые данные.

Изменение устройства, магазина, количества или существенной связи не переносит старое
решение молча. Проекция немедленно перестаёт применять устаревшее решение, очередь показывает
причину повторного открытия и прошлую историю. Автоматический обработчик не перетирает
подтверждённое ручное исключение или распределение.

## Расчёт и качество

Числитель формируется из разрешённых количеств гарантий за вычетом связанных возвратов,
сгруппированных по периоду и продавцу продажи устройства. Период документа гарантии
сохраняется отдельно для финансовой сверки. Полностью возвращённая гарантия даёт нулевой
вклад; превышение возврата над продажей требует отдельной диагностики, а не маскировки clamp.

Для известных кандидатов предварительность относится к их типам и исходным периодам.
Для отсутствующей связи нельзя уверенно назвать продавца и исходный период; показывается
общая неразрешённая очередь магазина. Ошибочно приписывать её автоматически финансовому
продавцу гарантии или объявлять все исторические периоды подтверждёнными.

Предлагаемая защита рейтинга: исключать затронутую гарантийную метрику из сравнения всех
сотрудников со средним магазина в затронутом периоде. Остальные attach-метрики остаются
доступны. Если привязку периода установить невозможно, нужна явно согласованная консервативная
политика; молчаливое ограничение только датой гарантии не защищает исходного продавца.
Исключение метрики не гарантирует математически неизменный общий балл: для абсолютного
требования «не снижать ранее показанный рейтинг» нужен отдельный механизм заморозки.

Неизменяемые опубликованные отчёты и снимки рейтинга не переписываются задним числом.
Живые показатели могут пересчитаться; новая опубликованная ревизия должна сохранять
версию формулы и происхождение атрибуции. Годовой отчёт не должен молча смешивать версии
гарантийной формулы в один сопоставимый показатель.

## Интерфейс

В карте допродаж — компактный блок «Не распределено гарантий: N», пояснение об исключённых
продажах и переход «Разобрать конфликты». N означает количество единиц, а не число строк.
У затронутых процентов — отметка «Предварительно», рядом числитель и знаменатель.

Очередь магазина показывает дату/номер финансового документа, товар гарантии, количество,
причину конфликта, кандидатов, состояние и историю. Не показывает данные чужого магазина.
Поиск исходной продажи поддерживает устойчивый идентификатор/номер и раскрывает устройства
в выбранном документе. Совпадение отображаемого номера само по себе не выполняет привязку.

Форма распределения показывает конкретные устройства и их тип; пользователь вводит
количество для каждого. Перед сохранением видны итог и остаток. Проверка суммы обязательна
на сервере. Исключение требует причину; откладывание сохраняет конфликт видимым.
Предупреждения доступны отдельно от очереди конфликтов, в том числе после разрешения.

## Предупреждения

- Гарантий больше, чем подходящих устройств, и процент выше 100% — диагностировать оба
  случая без автоматического обрезания корректного количества.
- Устройство возвращено при активном остатке гарантии — отдельная согласованность.
- Гарантия продана существенно позже устройства — порог предстоит определить; до этого
  интерфейс может показывать точное число дней без произвольного утверждения «поздно».
- Один товар гарантий используется для обоих типов — информировать о смешанном применении;
  это не основание менять товарную классификацию. Критерий «регулярно» требует порога/окна.

## Открытые решения

1. Возврат устройства в следующем периоде: исправлять базу исходного периода или уменьшать
   текущую? Рекомендация — исходный период для двух гарантийных метрик, оставив денежные
   показатели и остальные attach-метрики на действующей методике. Заказчик запросил
   рекомендацию; это пока рекомендация, а не явно подтверждённое решение.
2. Область защиты рейтинга при полностью неизвестном исходном периоде/продавце.
3. Межмагазинная продажа гарантии: автоматическое связывание запрещено до отдельного
   решения об аналитическом магазине и доступе. Руководитель не может читать чужой магазин.
4. Порог поздней гарантии и критерий регулярного смешанного использования товара.
5. Точное поддерживаемое поле связи LiveSklad, его область уникальности и связь до уровня
   позиции устройства; нужны обезличенные примеры контракта, а не эвристическое имя поля.

### Рекомендация по возврату устройства

За август продано 10 устройств с 8 гарантиями. В сентябре возвращено одно устройство
с одной гарантией: живой гарантийный показатель августа становится 7/9; сентябрьский
показатель по его собственным устройствам не изменяется. Денежные возвраты остаются
сентябрьскими операциями. Ранее опубликованный неизменяемый отчёт не переписывается.

Если вернули только устройство, числитель не уменьшается без возврата гарантии: результат
8/9 и отдельная проблема согласованности. Если знаменатель стал нулевым, процент `null`,
а активная гарантия и предупреждение остаются видимыми. Данные не обрезаются до 100%.

## Матрица обязательных сценариев

| Сценарий | Результат |
|---|---|
| Только Б/У iPhone/Samsung в документе | Автоматически Б/У |
| Только новые/ASIS/ASIS+ iPhone или новые Samsung | Автоматически новые |
| Несколько устройств одного подходящего типа | Тип определяется автоматически |
| Одновременно новые и Б/У устройства | Конфликт, выбор устройств и распределение |
| Отдельная гарантия и единственная точная исходная продажа | Тип, дата и продавец устройства |
| Несколько точных возможных продаж | Конфликт со списком кандидатов |
| Точная исходная продажа смешанная | Конфликт, выбор конкретного устройства |
| Связь не найдена | Конфликт, без автоматической эвристической связи |
| Точная связь с iPad/Watch/другим неподходящим устройством | Конфликт неподходящего типа |
| Гарантий больше устройств одного типа | Тип определён, предупреждение о количестве |
| Полный возврат гарантии | Нулевой итоговый вклад в числитель |
| Частичный возврат однозначно связанной гарантии | Уменьшение связанного количества |
| Частичный возврат смешанного распределения без точного устройства | Конфликт, ручной выбор |
| Возврат с найденной исходной гарантией | Наследование её связи, с проверкой неоднозначности |
| Возврат без найденной исходной гарантии | Конфликт, поиск исходной гарантии |
| Устройство возвращено, гарантия активна | Отдельная проблема согласованности |
| Повторная синхронизация без существенного изменения | Ручное решение сохраняется |
| Существенно изменился источник или цель | Конфликт открывается повторно, история сохраняется |
| Попытка руководителя связать данные чужого магазина | Отказ без раскрытия данных |

Порядок работ, зависимости, затронутые компоненты, проверки и критерии завершения вынесены
в [план реализации attach-rate](attach-rate-implementation-plan.md). Он охватывает новую
атрибуцию гарантий, source employee остальных возвратов, расхождения с DOCX, миграции,
API/интерфейс, рейтинг/Weekly Review/отчёты и подготовку исторических данных.

Этот документ сохраняет продуктовые требования и краевые случаи; план управляет порядком
реализации. Оба документа остаются проектными до проверки кода и извлечения принятых правил
в ADR и действующие контракты. Публикация новой методики — отдельный этап после локальной
приёмки с доказательством неизменности финансовых данных.
