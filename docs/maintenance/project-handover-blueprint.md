# Архитектура документации для передачи проекта

## Назначение и границы

Это **план комплекта**, а не утверждение, что передача состоялась или все сведения проверены.
Владелец проекта заполнит шаблоны после проверки источников. Пока пустая ячейка означает
`Не установлено`, а не отсутствие компонента, доступа или задачи. Дата `review_by` означает
пересмотр плана, а не срок завершения передачи.

## Согласованный способ передачи

Владелец подтвердил 2026-10-01 последовательность: довести код до рабочего состояния,
проверить его, развернуть на сервере без GitHub, разместить там полные исходники и документацию
и предоставить доступ новому разработчику. Наполнение документов выполняется позднее владельцем.
GitHub не является обязательной частью будущей передачи; локальная Git-история сохраняет
происхождение изменений и может передаваться вместе с проектом без внешнего Git-хостинга.

Документация хранится в `docs/` той же копии репозитория, что и передаваемый код. При заполнении
на сервере изменения сохраняются в Git этой копии. Исходники и документация должны иметь
резервную копию вне сервера. Их размещение не означает публикацию через web-сервер.

В будущем индексе передачи указать абсолютный путь к проекту на сервере, точку входа в `docs/`,
способ получить копию проекта, место внешней резервной копии по безопасному идентификатору и
роль, управляющую доступом. Конкретный серверный путь пока не выбран. В инфраструктурной карте
отдельно указать, откуда запускаются рабочие сервисы и где можно собирать и проверять изменения.
Изучение проекта на сервере не требует изменения работающих сервисов.

### Подготовка выпуска без GitHub

В текущем [release-safety.sh](../../deploy/bin/release-safety.sh) проверки образов прямо требуют
GHCR references и проверяют происхождение удалённых образов. Действующий
[deployment runbook](../runbooks/production-deployment.md) также описывает CI и GHCR.
Поэтому доставка без GitHub требует отдельной доработки процедуры и проверок до первого
такого выпуска; договорённость о способе передачи сама по себе их не меняет.

В `work-items.md` включить задачу выбора и проверки доставки готовых образов без GitHub
(например, архивом), сохранив проверку целостности и связи образов с исходниками, локальные
backend/frontend gates, backup, миграционный preflight и проверку результата на сервере.
Обновить скрипты, их тесты и runbook вместе. Способ доставки пока не выбран и не проверен.

## Маршрут нового разработчика

1. Открыть [общий индекс](../README.md) и действующие
   [контракты](../current/README.md); сверить наблюдавшееся production-состояние только по
   [project-state](../current/project-state.md).
2. Прочитать будущий `docs/maintenance/project-handover/README.md`: статус передачи,
   порядок запуска, карту документов, границы проверенного и контактные роли.
3. Открыть будущий `work-items.md`: незавершённые задачи, решения, зависимости и следующий
   безопасный шаг. Исторические отчёты из [history](../history/README.md) использовать как
   свидетельства на дату, не как актуальные инструкции.
4. По карте компонентов перейти к текущим контрактам, OpenAPI, миграциям, тестам, UI и runbook.
5. По карте инфраструктуры и реестру доступов установить, какие роли и окружения требуются;
   сами секреты передаются отдельно через согласованный защищённый канал. Исполняемые действия
   брать только из [runbooks](../runbooks/README.md) с подходящим статусом и verification gate.

## Слои и место каждого документа

| Слой | Планируемый путь / существующий источник | Отвечает на вопрос | Правило |
|---|---|---|---|
| Вход | `docs/maintenance/project-handover/README.md` | С чего начать, что проверено, где найти остальное? | Краткий индекс; не копирует production-снимок. |
| Остаток работ | `docs/maintenance/project-handover/work-items.md` | Что делать дальше, в каком порядке и почему? | Рабочие задачи и открытые решения; реализованное поведение отдельно. |
| Компоненты | `docs/maintenance/project-handover/components/<name>.md` | Кто владеет модулем, как проходит поток данных? | Ссылки на current-контракты и конкретный код. |
| Инфраструктура | `docs/maintenance/project-handover/infrastructure.md` | Какие окружения, сервисы и зависимости существуют? | Наблюдаемое runtime-состояние только ссылкой на project-state. |
| Доступы | `docs/maintenance/project-handover/access-register.md` | Какую роль кому передать и как подтвердить доступ? | Только метаданные доступа; без значений секретов и персональных учётных данных. |
| Транспорт API | [OpenAPI](../../contracts/openapi/current.json) + [API index](../current/api/README.md) | Методы, paths, параметры, схемы, семантика? | OpenAPI задаёт shape, тематический current-файл — правила и ограничения. |
| Модель данных | [Database](../current/architecture/database.md) + [migrations](../current/architecture/migrations.md) | Какие сущности, поля, ключи и изменения схемы? | Flyway и тесты — источник точной схемы; компонент связывает таблицы с use case. |
| Операции и безопасность | [Runbooks](../runbooks/README.md) + [Security](../security/README.md) | Как безопасно выполнять и проверять операции? | Handover не заменяет проверенный runbook или security policy. |
| Финальная фиксация | `docs/history/handoffs/YYYY/MM/<name>.md` | Что действительно передано на указанную дату? | Датированное evidence после фактической приёмки; не текущий контракт. |

Планируемые файлы создаются по мере заполнения. Каждый новый документационный файл сразу
регистрируется в [inventory](documentation-inventory.tsv) и получает подходящий lifecycle
metadata. Рабочие файлы остаются `working/draft`; когда содержание подтверждено, правила и
контракты переносятся в `current`, решения — в ADR, факт передачи — в `history`.

## Навигация и связи

```text
docs/README.md
  └─ project-handover-blueprint.md (этот план)
       └─ project-handover/README.md (будущий индекс передачи)
            ├─ work-items.md ──> current / ADR / код / тест / evidence
            ├─ infrastructure.md ──> project-state / deploy / runbooks / security
            ├─ access-register.md ──> security / runbooks / защищённый реестр владельца
            └─ components/<name>.md ──> product / API / frontend / migrations / тесты
```

Правило ссылок: индекс указывает на дочерние документы; компонент указывает на канонические
контракты; задача указывает на затронутые компоненты и доказательство завершения. Название
компонента стабильно и соответствует домену или интеграции, а не номеру релиза. У каждого
утверждения о текущем поведении есть ссылка на код/контракт и проверку; у неизвестного факта —
ответственный и способ проверки.

## Начальная карта компонентов для заполнения

Это маршруты к исходникам и контрактам после ознакомления с проектом, а не аудит готовности
каждого модуля. По каждому направлению создать карточку по
[шаблону компонента](templates/handover-component.md); при необходимости разделить её на несколько.

| Направление | Код от корня репозитория | Откуда начать чтение |
|---|---|---|
| Синхронизация и LiveSklad | `backend/.../integration`, `backend/.../sync` | [Синхронизация](../current/integrations/livesklad/synchronization.md) |
| Каталог и классификация | `backend/.../product`, `frontend/src/admin` | [Классификация](../current/product/classification.md) |
| KPI, допродажи и гарантии | `backend/.../metrics`, `frontend/src/dashboard`, `frontend/src/warranties` | [Показатели](../current/product/business-metrics.md), [attach-rate](../current/product/attach-rate.md) |
| Сотрудники, рейтинг, планы и смены | `backend/.../employee`, `backend/.../performance`, `frontend/src/employees`, `frontend/src/plan-schedule` | [Сотрудники](../current/product/employees-and-rating.md), [планы и смены](../current/product/plans-and-shifts.md) |
| Зарплата и отчёты | `backend/.../salary`, `backend/.../report`, `frontend/src/payroll`, `frontend/src/reports` | [Зарплата](../current/product/payroll.md), [отчёты](../current/product/reports.md) |
| Недельные разборы, AI и уведомления | `backend/.../interpretation`, `backend/.../notification`, `frontend/src/insights` | [AI index](../current/ai/README.md) |
| Пользователи и права | `backend/.../auth`, `backend/.../common/config`, `frontend/src/auth` | [Authentication и access](../security/authentication-and-access.md) |
| Качество данных и аудит | `backend/.../quality`, `backend/.../audit`, `frontend/src/quality` | [Качество данных](../current/product/data-quality.md), [аудит](../current/architecture/audit-and-telemetry.md) |
| Общие контракты и эксплуатация | `backend/.../common`, `frontend/src/api`, `contracts/openapi`, `deploy`, `scripts`, `monitoring` | [Архитектура](../current/architecture/application.md), [API](../current/api/README.md), [runbooks](../runbooks/README.md) |

Здесь `backend/.../` означает `backend/src/main/java/com/storeanalytics/`.
Главный поток для схемы связей: LiveSklad → нормализация и PostgreSQL → расчёты и сохранённые
результаты → HTTP API → React. Фоновые задачи и внешние уведомления обозначать отдельными ветвями.

## Источники остатка работ

Перед заполнением статусов перечитать актуальные контрольные точки:

- [Каталог](catalog-classification-architecture.md): локальный переход на новые категории,
  дата активации, сверка назначений и сохранность истории, проверки перед выпуском.
- [Аналитика продавцов](weekly-review-seller-first-handoff.md): согласованность с каталогом,
  локальный end-to-end, исторический состав команды и восстановление пропущенных недель.
- [Новая зарплата](payroll-redesign.md) и [план реализации](payroll-redesign-implementation-plan.md):
  подтверждённые решения, проверка исходных данных и ещё не реализованные этапы новой методики.
- [Project state](../current/project-state.md): последнее наблюдение сервера и эксплуатационные
  ограничения; дата проверки отдельных частей может различаться.

У каждой задачи указать, обязательна ли она для ближайшего рабочего выпуска или передаётся
как следующий этап. Состав ближайшего выпуска ещё нужно определить: изучение проекта не
означает, что все перечисленные разработки обязательны для его запуска или уже завершены.
Документацию сверять с кодом и тестами; расхождения фиксировать задачами, а не снимать по
наличию статуса `current`. Ознакомление с исходниками не заменяет запуск и проверки.

## Порядок заполнения

1. Заполнить индекс и остаток работ, отдельно отметить `проверено`, `со слов` и
   `не установлено`. Зафиксировать ссылку на незавершённую локальную работу, не объявляя её
   production-состоянием.
2. Составить список компонентов из кода и индексов current. Для каждого заполнить карту
   зависимостей и ссылки; подробные поля и endpoints перечислять только там, где нужна связь
   с use case, всегда со ссылкой на каноническую схему.
3. Проверить инфраструктуру по конфигурации и доступным наблюдениям; описать согласованный
   способ доставки без GitHub, пути к исходникам/документации и резервное копирование.
   Сведения о фактическом развёртывании подтвердить после выпуска.
4. С владельцами систем заполнить доступы без секретных значений; провести выдачу/отзыв по
   security/runbook и сохранить лишь безопасное подтверждение.
5. Проверить доступ получателя к проекту и документации на сервере. Провести onboarding
   в локальном или изолированном окружении: запуск, один запрос, один путь изменения кода,
   один тест, поиск процедуры восстановления. Зафиксировать пробелы в `work-items.md`.
6. После фактической передачи создать датированное handoff evidence со ссылками на версию
   комплекта, приёмку и оставшиеся ограничения.

## Правила качества

- Не повторять release ID, schema version, image digest и production flags за пределами
  [project-state](../current/project-state.md).
- Не переносить secret values, приватные ключи, токены, пароли, полные env-файлы, персональные
  сведения, provider payload или бизнес-скриншоты в Git. Реестр доступа хранит только тип,
  владельца, место хранения по безопасному идентификатору и процедуру передачи.
- Для нового API/поля менять OpenAPI/миграцию и действующий тематический контракт вместе с
  кодом. Handover-карта лишь помогает найти их.
- Не выдавать draft runbook, proposal, локальный код или прошлый audit за подтверждённый
  production-факт. Открытый вопрос сохранять открытым до решения владельца.
- При payroll-вопросах начинать с [рабочего входа](payroll-redesign.md), а решение заказчика
  фиксировать в соответствующем реестре решений.

## Критерий закрытия плана

Все строки матрицы заполнены или явно помечены как неизвестные с владельцем; ссылки проходят
проверку; проверенный код и документация доступны получателю на сервере, внешняя резервная
копия доступна; новый разработчик прошёл onboarding; финальное evidence записано в
`history/handoffs`. Выпуск без GitHub подтверждается обновлённой процедурой и её проверками.
До этого план остаётся `draft`. Результат извлечения: **ожидается**.
