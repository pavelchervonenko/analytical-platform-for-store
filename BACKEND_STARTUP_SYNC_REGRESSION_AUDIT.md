## Выявленные дефекты и риски

### P0/P1. Backend не запускался из-за двух bean с именем `annualReportScheduler`

Наблюдение:

```text
BeanDefinitionOverrideException: Invalid bean definition with name 'annualReportScheduler'
... BackgroundSchedulingConfiguration ...
... AnnualReportScheduler.class ...
```

Предполагаемая причина: имя компонента `AnnualReportScheduler` столкнулось с именем `@Bean` для планировщика задач. Включать `spring.main.allow-bean-definition-overriding=true` нельзя: это скроет архитектурную ошибку и сделает выбор bean неявным.

Текущее направление исправления, которое необходимо проверить: отдельное имя инфраструктурного bean, например `annualReportTaskScheduler`, и явный qualifier/ссылка из scheduled-компонента.

Проверить:

- полный старт ApplicationContext с включенными планировщиками;
- уникальность имен всех `@Component`, `@Service`, `@Configuration` и `@Bean`;
- явную привязку каждого специализированного scheduler/executor;
- корректное завершение scheduler при остановке приложения;
- отсутствие зависимости от разрешения bean overriding.

Искать аналоги: все классы `*Scheduler`, `*Worker`, `*Executor`, конфигурации фоновых задач и именованные bean.

### P0/P1. Импорт категорий создавал несовместимую provisional identity товара

Наблюдения:

- импорт классификации создавал товары по каталожному `code` до синхронизации продаж;
- LiveSklad затем присылал настоящий внешний идентификатор и тип товара;
- товар не сопоставлялся с уже созданной provisional-записью;
- продажи массово становились `unmapped` либо создавались дубликаты;
- backfill падал в фазе `SALES`;
- PostgreSQL фиксировал ошибку ограничения/триггера: `source identity cannot be changed`.

Это не только проблема UI-классификации. Она нарушает инварианты идентичности товара и может искажать KPI, маржу, зарплату и качество данных.

Текущее направление исправления, которое необходимо проверить:

- поиск сначала по стабильному external ID, затем осторожный fallback по `code` в рамках одного connection/source;
- атомарная операция вроде `claimLiveSkladIdentity` для одноразового перевода provisional identity в фактическую;
- миграция `V19__allow_provisional_product_identity_claim.sql`, разрешающая только узкий переход provisional → фактическая identity;
- одна и та же логика в продажах и возвратах.

Проверить инварианты:

- фактическая identity после назначения больше не изменяется;
- код не объединяет товары разных подключений;
- неоднозначный код не выбирается произвольно;
- повторный импорт и повторная синхронизация идемпотентны;
- конкурентные sales/returns/import не создают дубликаты;
- ошибка транзакции не оставляет частично назначенные категории;
- миграция безопасна и для пустой БД, и при обновлении существующей схемы V18 → V19.

Обязательные сценарии:

1. Классификация → продажи.
2. Продажи → классификация.
3. Классификация → возвраты без предварительной продажи.
4. Повторный импорт того же файла.
5. Два товара с одинаковым code в одном connection.
6. Одинаковый code в разных connections.
7. Конкурентная попытка claim одной provisional-записи.
8. Синхронизация перекрывающихся периодов без удвоения документов и позиций.

### P1. Синхронизация возвратов отклоняла допустимый ответ `/cash-items`

Наблюдение из лога:

```text
Return sync ... failed during cash-items because response-data-incomplete with LiveSkladException
```

При диагностике фактического ответа LiveSklad было получено 20 cash-items, при этом поле `type` присутствовало только у 14. Адаптер требовал `type` у каждого элемента и отклонял весь ответ, хотя для выбора возвратных позиций строгая семантика нужна не всем элементам.

Текущее направление исправления, которое необходимо проверить: optional/nullable поле `type` на транспортном DTO и строгая проверка только там, где поле необходимо для бизнес-решения, например для позиции возврата.

Проверить:

- sanitized fixture реального ответа: поле отсутствует, равно `null`, содержит известное и неизвестное значение;
- неизвестное новое значение enum не ломает весь ответ без необходимости;
- невалидная возвратная позиция изолируется или завершает фазу с понятной безопасной ошибкой;
- пустые и частичные страницы, пагинация, повторяющиеся записи;
- лимиты размера/кардинальности ответа сохраняют защиту от resource exhaustion;
- raw-аудит не сохраняет избыточные персональные данные и секреты.

Искать аналоги во всех LiveSklad DTO: слишком строгие `required`, primitive вместо nullable, закрытые enum, обязательные вложенные объекты и списки.

### P1. `/period-quality` возвращал 500 из-за rollback-only транзакции

Наблюдение: `StorePeriodQualityService` ловил ожидаемое исключение `PerformancePlanNotFoundException` внутри общей read-only транзакции и пытался представить отсутствие плана как показатель качества. Однако вложенная транзакционная операция уже помечала транзакцию rollback-only, поэтому на выходе возникал `UnexpectedRollbackException`, а frontend показывал «Данные временно недоступны».

Текущее направление исправления, которое необходимо проверить: orchestration без общей транзакции (`Propagation.NOT_SUPPORTED`) либо явный query API, возвращающий optional/business state без исключения и без rollback-only.

Проверить:

- отсутствие плана возвращает HTTP 200 и предусмотренное contract v7 состояние качества;
- настоящее падение БД не маскируется как «план отсутствует»;
- все подзапросы читают согласованный store/period;
- авторизация доступа к магазину применяется ко всем веткам агрегатора;
- Testcontainers-тест действительно воспроизводил старую ошибку и падает без исправления.

Искать аналоги: агрегаторы/дашборды, которые ловят исключения внутри `@Transactional`, особенно `NotFound`, optimistic lock, validation и integration exceptions.

### P1. Диагностика LiveSklad теряла HTTP-статус и стадию сбоя

Ранее журнал содержал только общий `LiveSkladException`/`SalesSyncException`, например:

```text
Synchronization phase SALES failed: SalesSyncException
```

Этого недостаточно, чтобы отличить 401/403, rate limit, 4xx контракта, 5xx поставщика, timeout, ошибку десериализации и локальное нарушение данных.

В рабочей копии добавлены `LiveSkladHttpException`, response guards и интеграционная observability. Необходимо проверить полноту решения.

Требования:

- хранить и логировать безопасные структурированные поля: resource/stage, upstream HTTP status, внутренний error code, retryable, attempt, correlation/request ID;
- не записывать токены, cookie, Authorization и полный сырой payload;
- корректно учитывать `Retry-After`;
- различать transport timeout, DNS/TLS, HTTP error, schema mismatch и persistence failure;
- не превращать non-retryable 4xx в бесконечные повторы;
- error summary задачи должен помогать оператору, но не раскрывать чувствительные данные пользователю.

Искать аналоги во всех внешних адаптерах и местах, где исключение оборачивается без сохранения cause/status/retryability.

### P1. Nullable backend-поля не полностью отражены в OpenAPI/TypeScript

Наблюдение: при отсутствии плана backend законно возвращал `storePlan.formulaVersion: null`, но сгенерированный TypeScript-контракт ожидал строку либо optional-поле без `null`. Frontend был вынужден расширить runtime-схему через `z.string().nullable()`.

Это временная защита потребителя, а не полноценное исправление контракта.

Проверить:

- является ли `null` официальной семантикой contract v7;
- Java DTO/OpenAPI schema описывает nullable точно;
- generated TypeScript после регенерации принимает тот же JSON без ручного расхождения;
- consumer contract test фиксирует пример «план отсутствует»;
- аналогичные nullable/optional расхождения во всех ответах dashboard, quality, payroll, reports, sync jobs;
- даты, decimal, UUID, enum и pagination одинаково трактуются backend и frontend.

### P1/P2. Слишком большое окно ручной синхронизации и разное поведение путей запуска

Наблюдение: ручная синхронизация продаж отвечала `Sales synchronization window is too large`. В коде использовался предел порядка `MAX_DETAILS_PER_RUN = 70`. Фоновая job могла уменьшать окно и повторять фазу, а прямой ручной endpoint завершался ошибкой.

Проверить архитектурное решение:

- тяжелая синхронизация должна запускаться как durable job, а не удерживать HTTP-запрос;
- API должно либо заранее валидировать период с понятным лимитом, либо всегда ставить задачу в очередь;
- worker должен адаптировать размер окна по фактической емкости и rate limit;
- лимиты должны быть конфигурируемыми, наблюдаемыми и согласованными для sales/returns;
- нельзя частично импортировать период и сообщить общий успех;
- повтор после ошибки должен быть идемпотентным.

### P1/P2. `WAITING_RETRY` выглядел как зависание

Наблюдение: backfill долго оставался в `WAITING_RETRY`, в выводе повторялись только status/phase/steps/retries. Это может быть штатным ожиданием после rate limit, но оператор не видел причины и времени следующей попытки.

Проверить:

- `nextAttemptAt`, retry reason/category и attempt/maxAttempts доступны contract v7;
- frontend показывает «ожидание до …», а не бесконечный неопределенный progress;
- backoff имеет верхнюю границу и jitter;
- после рестарта задача продолжает работу;
- исчерпание попыток переводит задачу в конечное состояние с диагностикой;
- несколько jobs не создают synchronized retry storm.

### P1/P2. Отмена RUNNING-задачи могла временно блокировать новый запуск

Наблюдение: отмена работающей задачи была кооперативной — выставлялся `cancelRequested`, но текущая операция должна была вернуть управление worker. Пока job считалась активной, новый ручной запуск блокировался.

Проверить:

- отмену `PENDING`, `WAITING_RETRY` и `RUNNING`;
- частоту проверки cancel flag между страницами/окнами;
- timeout внешнего HTTP-вызова;
- lease expiry и восстановление после падения процесса;
- отсутствие двух одновременно исполняющих одну job workers;
- понятные состояния `CANCEL_REQUESTED`/`CANCELLED`, если они предусмотрены контрактом;
- возможность безопасно повторить тот же период после завершенной отмены.

### P1. Фактический runtime-стек не совпал с первоначально зафиксированным

Первоначально проект описывался как Spring Boot 3.5.3, но реальный лог запуска показывал Spring Boot 4.1.0, Spring 7.0.8, а связанный стек включал новые major-версии компонентов.

Не нужно автоматически понижать версии. Требуется установить, является ли upgrade осознанным и завершенным.

Проверить:

- единый источник версии в Gradle, lockfile, документации и deployment-конфигурации;
- совместимость springdoc, Security, JPA/Hibernate, Jackson, Testcontainers, actuator и observability;
- отсутствие случайного смешения примеров/настроек Boot 3 и Boot 4;
- поддерживаемую Java-версию и базовый Docker image;
- reproducible dependency verification и отсутствие незапланированных dynamic versions.

### P2. Скрипт подготовки демо имел ошибки и недостаточный preflight

Зафиксированные случаи:

- `jq` завершался синтаксической ошибкой при формировании `{periodStart: $start, periodEndInclusive: $end}` из-за shell quoting;
- импорт категорий сначала обработал 2513, затем ожидался 2514-й код;
- backfill завершался в `SALES`, а скрипт мог долго показывать `WAITING_RETRY` без достаточного пояснения;
- пользователю приходилось вручную диагностировать порты, БД, учетную запись и состояние job.

Проверить `scripts/prepare-local-demo.sh`:

- `shellcheck` и тест запуска из Bash;
- строгий режим shell без утечки секрета;
- пароль не попадает в argv, history, trace и логи;
- проверка наличия `jq`, `curl`, Docker/PostgreSQL и нужных версий;
- проверка доступности backend и contract version;
- проверка роли администратора, доступного connection/store;
- корректная обработка HTTP non-2xx и не-JSON ответа;
- bounded polling с timeout;
- понятный вывод `nextAttemptAt` и последней безопасной ошибки;
- повторный запуск не дублирует данные;
- период интерпретируется в timezone магазина, а не локальной timezone shell;
- никаких автоматических destructive reset/delete без отдельного явного подтверждения.

## Операционные проблемы, которые нельзя путать с дефектами бизнес-логики

Эти случаи встретились при запуске. Они не всегда означают дефект backend, но проект должен предотвращать их понятным preflight и документацией.

### Конфликт PostgreSQL на `127.0.0.1:5432`

В WSL уже работал системный PostgreSQL 14, а Docker Compose поднимал PostgreSQL 16. Backend подключался не к тому экземпляру и получал ошибку аутентификации `SQL State 28P01`.

Проверить:

- явный и конфигурируемый dev port;
- health/preflight, показывающий серверную версию, database и user без секрета;
- одинаковые значения Compose и Spring datasource;
- отсутствие неявного fallback на локальную БД.

### Порт 8080 был занят старым процессом backend

Проверить понятное сообщение диагностики и локальную инструкцию по поиску процесса. Не завершать чужой процесс автоматически.

### Короткий ключ security telemetry

Приложение корректно падало при слишком коротком pseudonymization key: это полезный fail-fast контроль. Нужно проверить, что `.env.example` и локальный preflight объясняют требование 32–256 символов и не предлагают production-секрет по умолчанию.

### `.env` нельзя было безопасно выполнить через `source`

Строка cron вида `IDEMPOTENCY_CLEANUP_CRON=0 15 4 * * *` является допустимой для dotenv-парсера, но не для Bash `source` без кавычек. Значения с пробелами приводили к `15: command not found`.

Рекомендация: не предлагать `source .env` как универсальный способ загрузки Spring/Compose dotenv. Если shell-export нужен, использовать отдельный валидный shell-файл или безопасный loader, не `eval`.

### `psql` пытался войти как `root`

Команда использовала не загруженные/не те shell-переменные и в контейнер ушел неверный пользователь. Команды диагностики должны брать конфигурацию из Compose либо явно указывать dev user/database без раскрытия пароля.

### Прочие ошибки эксплуатации

- Docker volume нельзя удалить, пока его использует контейнер — это ожидаемая защита Docker.
- `docker compose ... up -d ps` трактует `ps` как имя сервиса; это ошибка команды, а не приложения.
- `npm ci` из корня без `package.json`/lockfile и запуск Vite не из `frontend/` — ошибка рабочей директории, а не backend.
- NVM, который долго скачивает Node.js, не относится к backend, но поддерживаемая версия Node должна быть зафиксирована и проверяться автоматически.

|---|---:|---:|---:|---:|---:|
| МАГАЗИН | 39 | 2 507 400 | 2 | 189 970 | 2 317 430 |
| МобиСфера | 19 | 999 070 | 0 | 0 | 999 070 |
| Итого | 58 | 3 506 470 | 2 | 189 970 | 3 316 500 |

Для `МАГАЗИН` также наблюдалась gross/list сумма `2 584 000`, отличная от фактической суммы `soldPrice = 2 507 400`. Проверь, какое поле по contract v7 является продажной выручкой и где учитываются скидки. Нельзя смешивать gross, фактическую оплату и net после возвратов.

В контрольной выборке число уникальных документов совпадало с общим числом, то есть явных дублей не было. Повтори сверку напрямую с API и с PostgreSQL, используя одинаковые границы периода, timezone, store ID, статусы документов и правила учета возвратов.

## Поиск аналогичных ошибок

Проверка не должна ограничиваться уже известными классами. Выполни систематический поиск по следующим шаблонам.

### Spring и транзакции

- одинаковые неявные имена `@Bean` и stereotype-компонентов;
- несколько executor/scheduler без qualifier;
- пойманное исключение внутри `@Transactional`, после которого метод продолжает работу;
- `REQUIRES_NEW`, `readOnly` и self-invocation с неожиданной семантикой;
- внешний HTTP-вызов внутри длинной DB-транзакции;
- отсутствие transaction timeout и избыточные блокировки.

### Интеграционные контракты

- обязательность полей третьей стороны, которую не гарантирует реальный payload;
- primitive там, где источник может вернуть `null`;
- enum без forward-compatible обработки;
- неограниченные массивы/строки/вложенность;
- неверная пагинация, inclusive/exclusive границы, DST и timezone;
- потеря HTTP status/cause/retryability при wrapping исключений;
- логирование токенов или персональных payload.

### Идентичность и идемпотентность

- natural key, который уникален только внутри connection/store;
- provisional-запись, которую невозможно безопасно привязать к external ID;
- upsert без защиты от конкурентной вставки;
- mutable external identity;
- повтор/перекрытие периода, создающее дубликаты;
- partial commit при падении страницы синхронизации;
- разные правила разрешения товара в sales, returns, inventory и classification.

### Очереди синхронизации

- разные лимиты прямого endpoint и worker;
- бесконечный retry для permanent error;
- retry storm без jitter;
- lease без восстановления или heartbeat;
- cancellation, которая никогда не достигает terminal state;
- две активные job одного типа/connection/периода;
- потеря прогресса после рестарта;
- успех при частично загруженном периоде.

### Backend–frontend контракт

- `nullable` против `optional`;
- decimal как binary floating point;
- enum/status, неизвестный старому frontend;
- разные трактовки даты без timezone;
- 200 с ошибкой внутри body или 500 для ожидаемого business state;
- отсутствие stable machine-readable error code;
- несогласованная пагинация и лимиты;
- endpoint, доступный frontend, но отсутствующий/небезопасный в backend authorization.

### Конфигурация и безопасность

- секреты в tracked-файлах, логах, argv, frontend bundle и Docker image layers;
- permissive CORS, CSRF/session cookie, proxy headers и client IP spoofing;
- actuator/metrics на публичном порту;
- отсутствие request/response size limits;
- SSRF через настраиваемый LiveSklad base URL;
- mass assignment и IDOR по store/user/connection ID;
- отсутствие rate limiting для login, sync и административных операций;
- непредсказуемое чтение `.env` разными инструментами.

## Обязательная матрица проверок

### Сборка и статический контроль

- backend compile и полный test suite;
- Checkstyle;
- Flyway validation;
- frontend clean install из `frontend/`, typecheck, unit tests, lint и production build;
- consumer contract tests против contract v7;
- `shellcheck scripts/prepare-local-demo.sh`;
- проверка отсутствия секретов и случайных backup-файлов в git/build context.

Используй реальные команды проекта, определив их по Gradle/npm scripts. Не утверждай, что `clean test`, JaCoCo или e2e прошли, если они фактически не запускались.

### Backend и база данных

1. Startup smoke с PostgreSQL 16 и scheduler enabled.
2. Все миграции на полностью пустой БД.
3. Обновление копии схемы V18 до V19.
4. Hibernate schema validation после Flyway.
5. Параллельный запуск двух экземпляров worker, если модель это допускает.
6. Рестарт процесса во время `RUNNING` и `WAITING_RETRY`.

### Синхронизация

1. Stores → employees → classification → sales → returns.
2. Stores → employees → sales → returns → classification.
3. Однодневный период с точной сверкой количества и сумм.
4. Повтор того же периода.
5. Перекрывающий период.
6. 401, 403, 404, 429 с `Retry-After`, 5xx, timeout и malformed JSON от upstream.
7. Ответ с missing/null/unknown полями.
8. Ответ выше лимита размера и кардинальности.
9. Отмена job в каждом активном состоянии.
10. Возобновление после рестарта и истечения lease.

### API и UI

1. Login admin и проверка назначения магазинов.
2. Получение stores и запуск sync только с разрешенной ролью.
3. Quality endpoint без плана — не 500.
4. Quality endpoint при настоящей DB-ошибке — корректная ошибка, не ложный business state.
5. `formulaVersion = null` проходит generated/runtime contract.
6. Job progress показывает phase, attempt, next retry и безопасную ошибку.
7. Correlation ID из UI находится в backend-логе.
8. Пользователь без доступа не может подобрать чужой store/job/connection по UUID.

## Критерии приемки

Проверку можно считать завершенной, когда:

- backend стабильно стартует без bean collision и без разрешенного overriding;
- схема создается с нуля и обновляется с V18 до V19;
- классификация, продажи и возвраты работают в любом допустимом порядке без duplicate/unmapped из-за provisional identity;
- однодневная сверка объясняет counts, gross, actual, returns и net;
- отсутствие плана не вызывает 500;
- LiveSklad failures имеют безопасную структурированную диагностику и корректную retry policy;
- job переживает рестарт, корректно отменяется и не зависает бессрочно;
- contract v7 одинаково понимается backend, OpenAPI generator, runtime validation и UI;
- локальный demo script либо успешно готовит данные, либо быстро завершается с точной инструкцией;
- для всех исправленных P0/P1 есть регрессионные тесты;
- все непокрытые риски явно перечислены, а не замаскированы успешным smoke-тестом.
